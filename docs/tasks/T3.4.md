### Лимит сканов: как устроено в SQL (миграция 0005)

- **Счёт**: сканы пользователя (`scans.user_id`; один user = одно устройство, `users.device_id`) с `created_at` за
  последние 24 ч, кроме самого проверяемого и кроме отклонённых лимитом (`stage='failed' and error='rate_limited'` —
  они ничего не стоили и не должны продлевать блокировку). Лимит: `users.created_at` моложе `new_account_hours` →
  `new_account_scans_per_day` (20), иначе `max_scans_per_day` (10). Числа — из `lithos.limits`.
- **Где проверяется**: (а) триггер `scans_apply_limit` before insert, только для клиентских вставок (`auth.uid() is not
  null`) — превышение ставит `stage='failed'`, `error='rate_limited'` прямо в вставляемую строку (под
  `pg_advisory_xact_lock` на пользователя — два параллельных insert не проскочат вдвоём; classid `'LIMT'` ≠ `'LITH'`
  воркера); (б) `enqueue_scan` — по такой строке бросает `rate_limited`, а для «чистой» строки повторяет проверку
  `scan_limit_exceeded` перед `pgmq.send` (страховка: скан вставлен до миграции / без JWT — покрыто интеграционным тестом).
  После 0006 клиент не может менять `scans.stage/error` (`42501`) — обход лимита через RLS-update закрыт.
- **Почему триггер, а не только RPC**: `raise exception` в plpgsql откатывает транзакцию целиком — записать
  `scans.stage/error` и бросить исключение в одном вызове `enqueue_scan` невозможно. Клиент вставляет `scans` до фото и
  `enqueue` (T1.4 `submitScan` шаг 1), поэтому запись делает триггер при insert, а исключение — RPC. Итог для клиента:
  и `P0001 'rate_limited'` из `enqueue_scan`, и `scans.error='rate_limited'` на строке.
- **Идемпотентность**: `scans.enqueued_at` ставится при первом `send`; повторный `enqueue_scan` для скана с
  `enqueued_at` или `stage<>'preflight'` возвращает `-1` (не ошибка), второе сообщение не шлётся, лимит не тратится. Лимит и
  идемпотентность — только для `scan_interactive`; `scan_dispute`/`scan_batch` — переанализ, не новый скан.
- **Единственное разрешённое дублирование чисел**: сид `lithos.limits` в миграции (SQL не импортирует TS). Тест
  `apps/worker/src/limits/limits-migration.test.ts` читает все миграции с `insert into lithos.limits` и сверяет
  значения с `SCAN_LIMIT_SEED` из shared. Менять число = править shared + новая миграция с новым сидом.

## Решения

- **Token bucket только на основной провайдер ступени.** Fallback и retry внутри `llm/` не ограничиваются: при отказе
  основного трафик и так падает (breaker), а второй провайдер редко под нагрузкой; двойной токен на каждый вызов
  «на всякий случай» вдвое занизил бы пропускную способность. Ёмкость bucket = RPM (burst до минуты).
- **Soft-бюджет режет тир только когда S3 реально пропущен** (`escalation='skipped_budget'`, ревью M2): replay или
  dispute с уже посчитанным Opus-результатом используют его как есть. Карточки без триггеров S3 ниже rare по построению.
  `provisional` не ставится (это не fallback, переанализ не планируется).
- **Hard-бюджет посреди цепочки** (после S2) не бросает скан: доходит до S4 как soft. Пауза — только до первого вызова.
- **Пауза по бюджету = новое сообщение с delay, а не `set_vt`**: pgmq не даёт уменьшить `read_ct`, а через `set_vt`
  третья пауза отправила бы скан в DLQ. `send(delay=600)` + `ack` старого — `read_ct=0`, попытка не считается.
- **`geo_anomaly` → `pending_review` только от epic** (`ANOMALY_REVIEW_MIN_TIER`). T2.1 ставил ревью при любой аномалии —
  приведено к spec §11 («эпический камень в точке, где порода невозможна — авторевью»). Сравнивается `internal_tier`
  (до clamp'а fallback/бюджета) — по постановке.
- **Расход за сутки — по `scans.created_at`** (UTC): скан, начатый в 23:59 и закончившийся в 00:01, идёт во вчера. Для
  предохранителя это несущественно; `scans.cost_usd` уже пересчитывается воркером после каждой ступени (T2.1), отдельной
  агрегации по `scan_results` не нужно.
- **`DAILY_BUDGET_USD=0` = выключено, `PROVIDER_RPM_*=0` = без лимита.** Нечисло/отрицательное → ошибка при старте.
- **Токен ждём не дольше 120 с** (`MAX_TOKEN_WAIT_MS`): дальше `RateLimitWaitError` → consumer: retry через очередь
  (`set_vt` 10 с), read_ct растёт — при затяжном шторме 429 скан дойдёт до DLQ, а не повиснет в слоте конвейера.
- **Колоночные права вместо доверия клиенту** (0006): RLS отвечает за «свои строки», grant — за «свои колонки».
  Воркер под service_role/postgres не затронут; `enqueue_scan` — security definer.
