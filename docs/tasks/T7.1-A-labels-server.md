## Уникальный ключ: `(scan_id, source, author_id)`, не `(scan_id, source)`

Источник и автор — разные измерения. Для `user_confirm`/`user_correct` автор всегда один (владелец скана),
поэтому на практике это «одна метка на источник», как в постановке. Но для будущего `expert` разные эксперты
независимо оценивают одну находку — это два разных наблюдения, схлопывать их в одну запись на
`(scan_id, source)` значило бы терять данные. `author_id` сделан `NOT NULL`: для `golden` (импорт эталонного
набора) это требует завести реальный идентификатор импортёра — решение и код оставлены потоку C.

## Что должен делать клиент (поток B)

- `user_confirm` — сервер сам переводит `cards.verification` из `ai` в `community`.
- `user_correct` — сервер вердикт **не** трогает. Клиент: (1) метка уже сохранена вызовом; (2) показать
  нейтральный текст («метка сохранена»), не «карточка исправлена»; (3) отдельно решить, вызывать ли
  `lithos.enqueue_scan(scan_id, 'scan_dispute')` для переанализа — очередь готова, не подключена.
- `record_label` отклоняет `expert`/`golden` — этой функцией их не пишут.

## Осталось потокам B и C

- B: кнопки «подтвердить»/«исправить» на `CardScreen`, выбор породы из справочника, тексты, `consent-copy.md`.
- C: экспорт с фильтром `training_opt_in`, идентификатор импортёра для `golden` (уникальный ключ), счётчик
  готовности по `matched_model`.

## Правки после ревью (оркестратор, 2026-09-30)

Ревью вернуло NEEDS_WORK: блокер и major. Обе правки — новой миграцией `0014_label_integrity.sql`, 0013 уже
применена и по правилам не правится.

### Блокер — исправлено: самоподтверждение выдавалось за проверку сообществом
`record_label` переводила `cards.verification` из `ai` в `community`, когда владелец подтверждал собственную
находку. Никакого сообщества в этом нет: второго независимого наблюдателя в системе не существует. При этом
интерфейс показывал «подтверждено сообществом», то есть прямо сообщал о независимой проверке, которой не
было. В базе самоподтверждение стало бы неотличимо от настоящего подтверждения, когда оно появится, и
испортило бы и доверие к признаку, и отбор в обучающую выборку — ровно то, ради чего задача делается.

Функция больше не трогает `lithos.cards` вообще. Факт «автор подтвердил» лежит в `lithos.labels` вместе с
источником и автором, оттуда его и читать. Значение `community` остаётся зарезервированным.

### Major — исправлено: порода метки не проверялась
`p_rock_class` проверялась только на непустоту. В `cards.rock_class` пишет доверенный воркер, а в метки —
конечный пользователь через RPC, где клиентские типы ничего не гарантируют. Добавлен справочник
`lithos.rock_classes` (66 пород) и внешний ключ на него, функция отвечает `unknown_rock_class`.

Справочник — второе разрешённое дублирование после сида `lithos.limits`: SQL не умеет импортировать
TypeScript. Источник истины остаётся `packages/shared/src/enums.ts`, а тест читает миграции и сверяет списки,
поэтому разъехаться они не могут.

### Minor — принято к сведению
Инварианты проверяются по тексту миграций, а не поведенческим тестом против базы. Для функции, отвечающей за
права, этого мало. Переписывать на поведенческий тест здесь не стал: в репозитории нет ни локальной базы для
тестов, ни соответствующей оснастки, заводить её попутно с этой задачей неправильно. Вместо этого проверка
сделана вручную на живой базе: у `anon` права на вызов нет, внешний ключ на месте, функция больше не меняет
статус проверки, прод-данные не затронуты. Полноценный поведенческий тест — хвост.

### Что изменилось для потока B
Подтверждение **не меняет** статус карточки. Интерфейс должен показывать «вы подтвердили» по наличию
собственной метки, а не по полю `verification`. Прочитать свою метку сейчас нечем: у таблицы нет политики
чтения, это надо добавить отдельной функцией.
