# T6.0 — Правки после прогона на телефоне, публичная витрина и compliance

Статус: **план к исполнению, решения приняты** · 2026-09-10 · ветка `design-refresh`

Источник: замечания Игоря после первого запуска в Expo Go + его решения по социальному слою.
Часть 1 — четыре подтверждённых дефекта. Часть 2 — публичная витрина. Часть 3 — compliance.
Часть 4 — как это исполнять (параллельные агенты, автопродолжение после лимитов).

## Решения владельца (приняты, не пересматривать)

1. **Витрина = публикация.** Карточка, добавленная в витрину, видна другим пользователям, в том числе на карте.
2. **Ленты не делаем.** Ни сейчас, ни в этой волне.
3. **Политики обновить** везде, где они противоречат новой модели.
4. **Compliance — часть работы,** а не «потом»: соглашения и согласия делаются в этой же волне, как заготовки.
5. **Исполнять несколькими агентами параллельно**, не одним.

## Что должно быть сделано к концу следующей сессии

План выполнен целиком: части 1–3 в коде и в документах, все гейты зелёные, ветка запушена, PR обновлён.

Состояние данных на момент диагностики (прод-Supabase): 1 пользователь, 2 скана, 2 карточки — обе с гео, обе
в ячейке `szrv5f` (Тбилиси, 41.674 / 44.823), дневник 2 из 3. Это важно для пунктов 3 и 4.

# Часть 1. Дефекты

## 1. Камера: полосатое затемнение внизу вместо градиента

**Что не так.** `apps/mobile/src/screens/CameraScreen.tsx:29,139–141,200–201`: затемнение собрано из шести
`View` с `flex: 1` и ступенями прозрачности `[0, .14, .34, .58, .8, .94]`. На OLED видны шесть чётких полос.
Так сделали, чтобы не тащить зависимость (комментарий в файле честно это фиксирует), но выглядит плохо.

**Как чинить.** Поставить `npx expo install expo-linear-gradient` (first-party модуль Expo, есть в Expo Go,
+~30 КБ) и заменить стопку на один градиент по прототипу
(`linear-gradient(to top, rgba(11,15,20,.94) 24%, rgba(11,15,20,0))`):

```tsx
<LinearGradient
  colors={['transparent', 'rgba(11,15,20,0.94)']}
  locations={[0, 0.76]}
  style={styles.fade}
  pointerEvents="none"
/>
```

Удалить `FADE_STEPS`, `styles.fadeStep`, оставить `styles.fade`.

**Не делать блюр.** `expo-blur` даёт другой эффект (размывает превью камеры под панелью) и стоит дороже по
производительности на живом кадре; в прототипе именно градиент.

**Приёмка.** На iPhone нижняя панель камеры уходит в фон без видимых границ; кнопка спуска и «Далее» читаются
на светлом кадре (проверить на белом песке/небе).

**Оценка.** 20 минут.

## 2. Коллекция и Профиль: нет верхнего safe area (Dynamic Island срезает контент)

**Что не так.** Из восьми экранов только эти два не используют `useSafeAreaInsets` (проверено grep'ом:
Camera/Map/Diary/Card/Result/Review — используют, Collection/Profile — нет). Обе вкладки открываются с
`headerShown: false` в `TabNavigator`, поэтому контент начинается с y=0: заголовок «Коллекция» и имя в
профиле лезут под статус-бар и вырез.

**Как чинить.**
- `CollectionScreen.tsx`: `const insets = useSafeAreaInsets()` → в `contentContainerStyle` добавить
  `paddingTop: insets.top + 8`. Обратить внимание: `contentContainerStyle` у `FlatList` сейчас статический
  объект `styles.content` — сделать массивом `[styles.content, { paddingTop: insets.top + 8 }]`.
- `ProfileScreen.tsx`: то же самое для `ScrollView`.
- Нижний инсет не трогать: таб-бар сам добавляет свой отступ.

**Отдельно проверить при исполнении** (тем же заходом, раз уж полезли в safe area): в альбомной ориентации и
на устройствах с «ушами» контент не должен уходить под скруглённые углы — но приложение
`orientation: portrait` (app.json), так что достаточно вертикального случая.

**Приёмка.** На iPhone 17 Pro (Dynamic Island) заголовок «Коллекция», счётчик карточек и имя в профиле
полностью видны и не подрезаны; при скролле контент уезжает под остров, а не начинается под ним.

**Оценка.** 15 минут.

## 3. Карта пустая: ни точек, ни зон

Это два разных дефекта под одним симптомом.

### 3a. Точек нет: `fitToCoordinates` уводит зум в сантиметры — **основная причина**

**Диагноз.** У обеих карточек координаты различаются на 3·10⁻⁸ градуса (~3 мм: два скана на одном месте).
`initialRegion` считается через `boundingRegion(...)`, где есть защита `minDelta = 0.02` (~2 км) —
и он корректен. Но `MapScreen.tsx:83–90` сразу после `onMapReady` вызывает

```ts
mapRef.current.fitToCoordinates(points.map(...), { edgePadding: FIT_PADDING, animated });
```

у которого **никакой нижней границы охвата нет**. Карта подгоняется под бокс 3×3 мм, уходит на максимальный
зум, где Apple Maps не отдаёт тайлы — отсюда пустой серый экран. Маркеры при этом формально есть, но
смотреть на них не на что.

**Как чинить.** Не звать `fitToCoordinates` на вырожденных наборах:

```ts
const span = Math.max(maxLat - minLat, maxLng - minLng);
if (points.length === 1 || span < MIN_FIT_SPAN /* 0.004 ≈ 400 м */) {
  const r = boundingRegion(points);           // уже с minDelta 0.02
  if (r) mapRef.current.animateToRegion(r, animated ? 350 : 0);
} else {
  mapRef.current.fitToCoordinates(coords, { edgePadding: FIT_PADDING, animated });
}
```

Логику охвата вынести в `lib/geo-math.ts` (`fitSpan(points)`) и покрыть тестом: одна точка, две совпадающие,
две разнесённые — чтобы больше не повторилось.

**Если после этого карта всё ещё пустая** (проверять именно в таком порядке):
1. Видна ли синяя точка своей геопозиции и компас — если нет, тайлы не грузятся вообще, и дело не в зуме.
2. Тогда проверить `react-native-maps` в Expo Go SDK 57: если нативный модуль не входит в Expo Go, карта
   работает только в dev-client сборке (`npx expo run:ios` / EAS dev build). Это меняет способ отладки, но
   не код.
3. Только если оба пункта отпали — смотреть RLS/данные (сейчас данные точно есть, проверено запросом).

### 3b. Зон нет: полигон рисуется только для 100 % закрытого дневника

**Диагноз.** `completedCells(diary, cards)` возвращает только ячейки, где найдено **всё** ожидаемое. У тебя
2 из 3 → ячеек ноль → полигонов ноль. Формально это работает по спецификации, но означает, что «зоны» на
карте не появятся почти никогда: закрыть дневник целиком — редкое событие.

**Решение принято** — рисовать **все посещённые ячейки**, а не только закрытые, с градацией:
- закрыта на 100 % — золотая заливка и обводка (как сейчас);
- есть находки, но не закрыта — тусклая заливка `accentTint` + пунктирная обводка, подпись «2 из 3».

Это делает карту сразу читаемой («вот где я был и насколько разобрался») и усиливает механику дневника.
Нужна функция `visitedCells(diary, cards)` рядом с `completedCells` + тесты.

### 3c. Мелочь: две карточки в одной точке накладываются

Два маркера в 3 мм друг от друга — это один кружок на экране. Минимальный шаг: при совпадении координат
показывать один маркер со счётчиком («2»), тап — список карточек этой точки. Кластеризацию целиком (библиотеку)
на прототипе не тянуть.

**Приёмка пункта 3.** На карте видны: 1 маркер-счётчик «2» в Тбилиси, ячейка `szrv5f` подсвечена тусклой
заливкой с подписью «2 из 3», масштаб — район города, а не сантиметры. Легенда снизу показывает «2 точки».

**Оценка.** 3a — 40 минут с тестами; 3b — 1 час с тестами; 3c — 40 минут.

## 4. Дневник места: технический `szrv5f` вместо названия и находки без фото

### 4a. Название места

**Что не так.** `DiaryScreen.tsx:129` печатает `Ячейка {cellId}` — то есть `Ячейка szrv5f`. В прототипе на
этом месте «Побережье, Сукко», а geohash — мелкой mono-строкой рядом (она у нас уже есть).

**Как чинить.** Обратное геокодирование центра ячейки через уже установленный `expo-location`:

```ts
const [place] = await Location.reverseGeocodeAsync(cellCenter(cellId));
// place: { city, district, subregion, region, name, street, country }
```

Собирать имя по приоритету `district → city`, иначе `city → subregion`, иначе `subregion → region`, иначе
`region`; для Тбилиси ожидаемо получится «Ваке, Тбилиси» или «Тбилиси».

Обязательно:
- **кэш в AsyncStorage по `cell_id`** (`lithos.place.<cell>`, TTL можно бесконечный — топоним не меняется):
  у Apple жёсткий рейт-лимит на обратное геокодирование, дёргать на каждый вход в дневник нельзя;
- **fallback на `Ячейка {cellId}`**, если: нет разрешения на гео (на iOS обратное геокодирование его требует),
  нет сети, или ответ пустой (море, безлюдная местность);
- geohash не выбрасывать — оставить в mono-строке под названием (сейчас там координаты, можно «szrv5f ·
  41.674, 44.823»).

**Долгосрочная альтернатива** (не сейчас, записать в бэклог): топоним считает воркер и кладёт в
`lithos.geo_cache` рядом с `expected_rocks` — тогда он общий для всех пользователей, работает офлайн и
не зависит от разрешения на гео на устройстве. Клиентский вариант — быстрый способ закрыть дефект сегодня.

### 4b. Находки в ячейке без фото

**Что не так.** `DiaryScreen.tsx:195` рендерит `<CardTile size="sm" …>` **без** `photoUrl` — плитки
показывают полосатый плейсхолдер. Это мой недосмотр при рестайле: в Коллекции и Профиле URL'ы подтягиваются
через `fetchPrimaryPhotoUrls`, а в Дневнике я это не подключил.

**Как чинить.** Как в `CollectionScreen`: состояние `urls`, после загрузки карточек ячейки —
`fetchPrimaryPhotoUrls(shownCards.map(c => c.scan_id))`, в `CardTile` передать `photoUrl={urls.get(c.scan_id)}`.

**Приёмка пункта 4.** Заголовок дневника — «Ваке, Тбилиси» (или ближайший осмысленный топоним), geohash
остался мелкой подписью; плитки находок показывают реальные фото; при отключённом гео/сети заголовок
деградирует до `Ячейка szrv5f` без ошибки.

**Оценка.** 4a — 1 час с кэшем и fallback'ами; 4b — 20 минут.

# Часть 2. Публичная витрина (социальный слой)

Модель: **витрина = публикация**. Кнопка «В витрину» на карточке публикует находку. Ленты нет.

## 2.1. Что видят другие и чего не видят

| Видно другим | Не видно никому, кроме владельца |
|---|---|
| фото карточки (лицевое) | точные координаты (только центр ячейки geohash-6, ~1,2 км) |
| порода, тир, score | другие, неопубликованные карточки |
| имя пользователя (если задано; иначе «Без имени») | сканы, отказы, история ступеней, стоимость |
| место с точностью до ячейки | дневник, витрина целиком, статистика профиля |
| дата находки | device_id, идентификатор аккаунта |

**Правило координат — не обсуждается:** наружу уходит только `cell_id`, координаты для чужой карты считаются
как центр ячейки на клиенте. Точные `lat/lng` не должны попадать ни в один публичный запрос — это проверяется
тестом на список колонок публичного представления.

## 2.2. Схема и доступ (миграция `0007_public_showcase.sql`)

```sql
alter table lithos.cards add column if not exists published boolean not null default false;
alter table lithos.cards add column if not exists published_at timestamptz;
create index if not exists cards_published_idx on lithos.cards(published, published_at desc) where published;

-- Публичное представление: только разрешённые колонки, точных координат нет по построению.
create or replace view lithos.public_finds as
select c.id, c.rock_class, c.tier, c.score, c.lore, c.name, c.user_name,
       c.cell_id, c.created_at, c.published_at, u.display_name as author_name
from lithos.cards c join lithos.users u on u.id = c.user_id
where c.published and not c.hidden and c.verification <> 'pending_review';
```

Важное:
- витрина сейчас **локальная** (AsyncStorage `lithos.showcase`) — её надо перенести на сервер (`published`),
  оставив миграцию локального списка при первом запуске: что было в витрине — предложить опубликовать, а не
  публиковать молча;
- на ревью (`pending_review`) и скрытые (после раскола) карточки не публикуются никогда;
- RLS: `select` на `public_finds` для `authenticated`; на саму `lithos.cards` публичного доступа не давать;
- **фото**: бакет приватный. Нужен доступ к лицевому фото опубликованной карточки — сделать через RPC
  `lithos.sign_public_photo(card_id)` (security definer, проверяет `published`, возвращает подписанный URL),
  либо через политику на `storage.objects` по списку опубликованных путей. Выбрать первое — меньше поверхность.

## 2.3. Что меняется в приложении

- **Карточка**: «В витрину» → «Опубликовать» с диалогом первой публикации (текст — `docs/legal/consent-copy.md`),
  подпись о статусе, «Убрать из витрины» → снятие публикации (мгновенно исчезает у других).
- **Карта**: слой чужих находок — маркеры по центру ячейки, визуально отличимые от своих (обводка/прозрачность),
  тап → карточка чужой находки в режиме «только чтение» (без разбора score и истории версий).
- **Дневник места**: раздел «Здесь находили другие» — агрегат по ячейке, усиливает механику дневника.
- **Профиль**: пункт «Мои публикации» — сколько опубликовано, снять всё одним действием.
- **Жалоба**: на чужой карточке — «Пожаловаться», запись в `lithos.reports`, скрытие после N жалоб `[решить N]`.

## 2.4. Порог включения

Пока пользователь один, чужих находок не будет. Это нормально: код и политика должны быть готовы,
UI должен корректно показывать пустое состояние («Здесь пока никто ничего не публиковал»).

# Часть 3. Compliance

Документы-заготовки лежат в `docs/legal/` (создаются в этой же волне):
`README.md` (что решить человеку), `data-map.md` (факты о данных), `privacy-policy.ru.md`,
`terms-of-use.ru.md`, `consent-copy.md` (готовые тексты для экранов).

## 3.1. Что нужно сделать в коде

1. **Переписать копию онбординга** — текущая обещает «снимки не публикуются и не показываются другим»,
   что противоречит витрине. Новый текст — из `consent-copy.md` §1.
2. **Экран пересогласия** для тех, кто видел старую формулировку: показывается один раз при первом запуске
   после обновления (флаг `prefs.consentVersion`), объясняет, что изменилось, и что по умолчанию ничего не
   опубликовано. Текст — `consent-copy.md` §2.
3. **Диалог первой публикации** — `consent-copy.md` §3.
4. **Обновить `PRIVACY_TEXT`** в `lib/settings.ts` — `consent-copy.md` §5.
5. **Новые пункты настроек**: «Мои публикации», «Обучение модели» (переключатель + флаг
   `lithos.users.training_opt_in`), «Удалить данные на сервере».
6. **Серверное удаление данных** — RPC `lithos.delete_my_data()` (security definer): сканы, фото в Storage,
   карточки, дневник, публикации. Сейчас есть только локальное стирание — это дыра в правах пользователя.
7. **Экран документов**: Настройки → «Политика конфиденциальности» / «Пользовательское соглашение» —
   рендер markdown из `docs/legal/` (скопировать в `apps/mobile/src/legal/` при сборке или зашить строкой).
   App Store требует рабочую ссылку на политику — нужна и веб-страница `[ЗАПОЛНИТЬ: где хостим]`.

## 3.2. Что должен решить человек (блокеры для стора, не для кода)

Оператор данных и контакт, юрисдикция, возрастной ценз, формулировка лицензии на опубликованные фото,
где хостится веб-версия политики. Все места помечены `[ЗАПОЛНИТЬ]` — см. `docs/legal/README.md`.

## 3.3. Чего сознательно не делаем сейчас

Аналитики нет и не добавляем (иначе появляются новые обязанности по раскрытию). Возрастной верификации нет.
Модерация — только жалобы и скрытие по порогу, без ручной очереди: при одном пользователе очередь не нужна,
но код жалоб должен быть на месте до того, как появится второй.

# Часть 4. Как исполнять

## 4.1. Параллельные агенты

Работа разбита на потоки, которые **не пересекаются по файлам** — это условие параллельности:

| Поток | Файлы | Зависимости |
|---|---|---|
| **A. Дефекты UI** | `CameraScreen`, `CollectionScreen`, `ProfileScreen` (только safe area), `+expo-linear-gradient` | нет |
| **B. Карта** | `MapScreen`, `lib/geo-math.ts`, `lib/diary.ts` (`visitedCells`), тесты | нет |
| **C. Дневник** | `DiaryScreen`, `lib/place-name.ts` (новый), `lib/cards.ts` (только чтение), тесты | нет |
| **D. Публикация: сервер** | миграция `0007`, RPC, `lib/publish.ts`, тесты | делает схему для E |
| **E. Публикация: клиент** | `CardScreen`, `ProfileScreen` (публикации), карта чужих находок | **после D** |
| **F. Compliance-код** | `WelcomeScreen`, экран пересогласия, `lib/settings.ts`, экран документов, RPC удаления | тексты из `docs/legal/` готовы |
