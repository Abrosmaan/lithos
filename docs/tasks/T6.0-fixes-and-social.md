# Часть 1. Дефекты

## 1. Камера: полосатое затемнение внизу вместо градиента

**Что не так.** `apps/mobile/src/screens/CameraScreen.tsx:29,139–141,200–201`: затемнение собрано из шести
`View` с `flex: 1` и ступенями прозрачности `[0, .14, .34, .58, .8, .94]`. На OLED видны шесть чётких полос.
Так сделали, чтобы не тащить зависимость (комментарий в файле честно это фиксирует), но выглядит плохо.

**Как чинить.** Поставить `npx expo install expo-linear-gradient` (first-party модуль Expo, есть в Expo Go,
+~30 КБ) и заменить стопку на один градиент по прототипу
(`linear-gradient(to top, rgba(11,15,20,.94) 24%, rgba(11,15,20,0))`):

```tsx
<LinearGradient
  colors={['transparent', 'rgba(11,15,20,0.94)']}
  locations={[0, 0.76]}
  style={styles.fade}
  pointerEvents="none"
/>
```

Удалить `FADE_STEPS`, `styles.fadeStep`, оставить `styles.fade`.

**Не делать блюр.** `expo-blur` даёт другой эффект (размывает превью камеры под панелью) и стоит дороже по
производительности на живом кадре; в прототипе именно градиент.

**Приёмка.** На iPhone нижняя панель камеры уходит в фон без видимых границ; кнопка спуска и «Далее» читаются
на светлом кадре (проверить на белом песке/небе).

**Оценка.** 20 минут.

## 2. Коллекция и Профиль: нет верхнего safe area (Dynamic Island срезает контент)

**Что не так.** Из восьми экранов только эти два не используют `useSafeAreaInsets` (проверено grep'ом:
Camera/Map/Diary/Card/Result/Review — используют, Collection/Profile — нет). Обе вкладки открываются с
`headerShown: false` в `TabNavigator`, поэтому контент начинается с y=0: заголовок «Коллекция» и имя в
профиле лезут под статус-бар и вырез.

**Как чинить.**
- `CollectionScreen.tsx`: `const insets = useSafeAreaInsets()` → в `contentContainerStyle` добавить
  `paddingTop: insets.top + 8`. Обратить внимание: `contentContainerStyle` у `FlatList` сейчас статический
  объект `styles.content` — сделать массивом `[styles.content, { paddingTop: insets.top + 8 }]`.
- `ProfileScreen.tsx`: то же самое для `ScrollView`.
- Нижний инсет не трогать: таб-бар сам добавляет свой отступ.

**Отдельно проверить при исполнении** (тем же заходом, раз уж полезли в safe area): в альбомной ориентации и
на устройствах с «ушами» контент не должен уходить под скруглённые углы — но приложение
`orientation: portrait` (app.json), так что достаточно вертикального случая.

**Приёмка.** На iPhone 17 Pro (Dynamic Island) заголовок «Коллекция», счётчик карточек и имя в профиле
полностью видны и не подрезаны; при скролле контент уезжает под остров, а не начинается под ним.

**Оценка.** 15 минут.

## 3. Карта пустая: ни точек, ни зон

Это два разных дефекта под одним симптомом.

### 3a. Точек нет: `fitToCoordinates` уводит зум в сантиметры — **основная причина**

**Диагноз.** У обеих карточек координаты различаются на 3·10⁻⁸ градуса (~3 мм: два скана на одном месте).
`initialRegion` считается через `boundingRegion(...)`, где есть защита `minDelta = 0.02` (~2 км) —
и он корректен. Но `MapScreen.tsx:83–90` сразу после `onMapReady` вызывает

```ts
mapRef.current.fitToCoordinates(points.map(...), { edgePadding: FIT_PADDING, animated });
```

у которого **никакой нижней границы охвата нет**. Карта подгоняется под бокс 3×3 мм, уходит на максимальный
зум, где Apple Maps не отдаёт тайлы — отсюда пустой серый экран. Маркеры при этом формально есть, но
смотреть на них не на что.

**Как чинить.** Не звать `fitToCoordinates` на вырожденных наборах:

```ts
const span = Math.max(maxLat - minLat, maxLng - minLng);
if (points.length === 1 || span < MIN_FIT_SPAN /* 0.004 ≈ 400 м */) {
  const r = boundingRegion(points);           // уже с minDelta 0.02
  if (r) mapRef.current.animateToRegion(r, animated ? 350 : 0);
} else {
  mapRef.current.fitToCoordinates(coords, { edgePadding: FIT_PADDING, animated });
}
```

Логику охвата вынести в `lib/geo-math.ts` (`fitSpan(points)`) и покрыть тестом: одна точка, две совпадающие,
две разнесённые — чтобы больше не повторилось.

**Если после этого карта всё ещё пустая** (проверять именно в таком порядке):
1. Видна ли синяя точка своей геопозиции и компас — если нет, тайлы не грузятся вообще, и дело не в зуме.
2. Тогда проверить `react-native-maps` в Expo Go SDK 57: если нативный модуль не входит в Expo Go, карта
   работает только в dev-client сборке (`npx expo run:ios` / EAS dev build). Это меняет способ отладки, но
   не код.
3. Только если оба пункта отпали — смотреть RLS/данные (сейчас данные точно есть, проверено запросом).

### 3b. Зон нет: полигон рисуется только для 100 % закрытого дневника

**Диагноз.** `completedCells(diary, cards)` возвращает только ячейки, где найдено **всё** ожидаемое. У тебя
2 из 3 → ячеек ноль → полигонов ноль. Формально это работает по спецификации, но означает, что «зоны» на
карте не появятся почти никогда: закрыть дневник целиком — редкое событие.

**Что предлагаю** (продуктовое решение, нужно твоё «да»): рисовать **все посещённые ячейки**, а не только
закрытые, с градацией:
- закрыта на 100 % — золотая заливка и обводка (как сейчас);
- есть находки, но не закрыта — тусклая заливка `accentTint` + пунктирная обводка, подпись «2 из 3».

Это делает карту сразу читаемой («вот где я был и насколько разобрался») и усиливает механику дневника.
Нужна функция `visitedCells(diary, cards)` рядом с `completedCells` + тесты.

### 3c. Мелочь: две карточки в одной точке накладываются

Два маркера в 3 мм друг от друга — это один кружок на экране. Минимальный шаг: при совпадении координат
показывать один маркер со счётчиком («2»), тап — список карточек этой точки. Кластеризацию целиком (библиотеку)
на прототипе не тянуть.

**Приёмка пункта 3.** На карте видны: 1 маркер-счётчик «2» в Тбилиси, ячейка `szrv5f` подсвечена тусклой
заливкой с подписью «2 из 3», масштаб — район города, а не сантиметры. Легенда снизу показывает «2 точки».

**Оценка.** 3a — 40 минут с тестами; 3b — 1 час с тестами; 3c — 40 минут.

## 4. Дневник места: технический `szrv5f` вместо названия и находки без фото

### 4a. Название места

**Что не так.** `DiaryScreen.tsx:129` печатает `Ячейка {cellId}` — то есть `Ячейка szrv5f`. В прототипе на
этом месте «Побережье, Сукко», а geohash — мелкой mono-строкой рядом (она у нас уже есть).

**Как чинить.** Обратное геокодирование центра ячейки через уже установленный `expo-location`:

```ts
const [place] = await Location.reverseGeocodeAsync(cellCenter(cellId));
// place: { city, district, subregion, region, name, street, country }
```

Собирать имя по приоритету `district → city`, иначе `city → subregion`, иначе `subregion → region`, иначе
`region`; для Тбилиси ожидаемо получится «Ваке, Тбилиси» или «Тбилиси».

Обязательно:
- **кэш в AsyncStorage по `cell_id`** (`lithos.place.<cell>`, TTL можно бесконечный — топоним не меняется):
  у Apple жёсткий рейт-лимит на обратное геокодирование, дёргать на каждый вход в дневник нельзя;
- **fallback на `Ячейка {cellId}`**, если: нет разрешения на гео (на iOS обратное геокодирование его требует),
  нет сети, или ответ пустой (море, безлюдная местность);
- geohash не выбрасывать — оставить в mono-строке под названием (сейчас там координаты, можно «szrv5f ·
  41.674, 44.823»).

**Долгосрочная альтернатива** (не сейчас, записать в бэклог): топоним считает воркер и кладёт в
`lithos.geo_cache` рядом с `expected_rocks` — тогда он общий для всех пользователей, работает офлайн и
не зависит от разрешения на гео на устройстве. Клиентский вариант — быстрый способ закрыть дефект сегодня.

### 4b. Находки в ячейке без фото

**Что не так.** `DiaryScreen.tsx:195` рендерит `<CardTile size="sm" …>` **без** `photoUrl` — плитки
показывают полосатый плейсхолдер. Это мой недосмотр при рестайле: в Коллекции и Профиле URL'ы подтягиваются
через `fetchPrimaryPhotoUrls`, а в Дневнике я это не подключил.

**Как чинить.** Как в `CollectionScreen`: состояние `urls`, после загрузки карточек ячейки —
`fetchPrimaryPhotoUrls(shownCards.map(c => c.scan_id))`, в `CardTile` передать `photoUrl={urls.get(c.scan_id)}`.

**Приёмка пункта 4.** Заголовок дневника — «Ваке, Тбилиси» (или ближайший осмысленный топоним), geohash
остался мелкой подписью; плитки находок показывают реальные фото; при отключённом гео/сети заголовок
деградирует до `Ячейка szrv5f` без ошибки.

**Оценка.** 4a — 1 час с кэшем и fallback'ами; 4b — 20 минут.

# Часть 2. Социальный слой — предложение (не реализовывать до решения)

## Где мы сейчас

Приложение полностью одиночное. В `rock-game-spec.md` §9 социальное описано, но узко: верификация
сообществом, обмен, витрина, и прямым текстом — **«Никаких чатов и лент на MVP»**. Ты просишь это
пересмотреть. Ниже варианты и что каждый стоит.

## Блокер, который надо решить до любого варианта

**Мы уже пообещали пользователю обратное.** Экран приветствия и `PRIVACY_TEXT` в настройках говорят дословно:
«Снимки не привязаны к имени, **не публикуются и не показываются другим пользователям**». Любая лента,
общая карта или публичный профиль этому противоречат.

Что потребуется:
1. Переписать копию онбординга и приватности (сейчас она сформулирована как обещание, а не как настройка).
2. Публикация — **только явный opt-in** на карточку («Показать находку сообществу»), по умолчанию выключено.
3. Для уже существующих пользователей — экран повторного согласия, а не тихая смена правил.
4. Никогда не публиковать точные координаты: наружу — ячейка geohash-6 (~1,2 км) или грубее geohash-5 (~5 км).
   Точка на своей карте остаётся точной, чужая — только ячейка. Это стандарт iNaturalist для чувствительных
   находок и защита от «этот человек каждое утро гуляет вот здесь».
5. Модерация: жалоба на карточку, скрытие по жалобе, ручной разбор. Ступень Gate (S1) уже отсекает не-камни и
   фото с экрана — это снимает часть мусора, но не заменяет модерацию.

Пункты 1–3 — это про доверие, их нельзя пропустить. Пункты 4–5 — про безопасность и юридические риски.

## Варианты

### A. Лента находок (то, что обычно называют «лентой»)
Хронологический или ранжированный поток опубликованных карточек: фото, порода, тир, место (ячейкой), автор.
- **Плюсы:** привычно, даёт «живость», лучший драйвер возвратов из всех вариантов.
- **Минусы:** самый дорогой по модерации; требует ранжирования, иначе тонет в обычной гальке; прямо
  противоречит §9 спеки; провоцирует «фарм ради ленты» (сканы ради показа, а не находки).
- **Стоимость:** таблица публикаций, публичный доступ к фото (отдельный бакет или edge-функция с подписью),
  лента с пагинацией, жалобы, лимиты. ~2 недели.

### B. Верификация сообществом (по спеке §9)
Очередь чужих карточек: «согласен с определением / другой вариант». Консенсус 3 голосов → статус
«подтверждено», +5 к score. Репутация растёт за совпадения с итоговым вердиктом.
- **Плюсы:** уже в спеке и в схеме БД (`cards.verification` умеет `community`); даёт **данные** — подтверждённые
  пары «фото + вердикт» идут в датасет для дообучения (§11); социальность с понятной целью, а не ради ленты;
  модерация проще — нет свободного текста, только голоса.
- **Минусы:** работает только при плотности пользователей (на двоих очередь пустая); не даёт «вау» сразу.
- **Стоимость:** таблица голосов, RLS, экран очереди, пересчёт статуса в воркере. ~1 неделя.

### C. Страница места (общая карта/дневник по ячейке) — **рекомендую начать с этого**
У каждой ячейки geohash-6 появляется общая страница: какие породы здесь находили (агрегат по всем
пользователям), сколько людей сканировали, лучшие находки места, твой прогресс против общего списка.
На карте — слой «здесь находили», не привязанный к личностям.
- **Плюсы:** приватно по построению (агрегат по ячейке, без имён и без точных точек); усиливает то, что уже
  есть — дневник и атлас; ценно **сразу**, даже когда пользователей мало (данные складываются, а не
  соревнуются); модерация почти не нужна — наружу идут породы и счётчики, а фото только по opt-in;
  напрямую чинит дефект 3b (карта наконец становится информативной).
- **Минусы:** это не «лента», ощущается спокойнее; не даёт ленты уведомлений.
- **Стоимость:** materialized view / агрегирующая таблица по ячейкам, публичная политика чтения на агрегат,
  расширение экрана дневника и карты. ~1 неделя.

### D. Публичные профили и витрина
Витрина (до 12 карточек) уже собирается локально — сделать её открываемой по ссылке, плюс страница профиля
с статистикой.
- **Плюсы:** дешевле всего, витрина уже есть в спеке §8 и в UI.
- **Минусы:** сам по себе почти не создаёт взаимодействия — некуда возвращаться.
- **Стоимость:** ~3 дня.

## Рекомендация

**Порядок C → B → A**, каждый следующий шаг — по метрикам предыдущего:

1. **C (Страница места)** — сначала. Приватно, чинит карту, работает при любом числе пользователей, не требует
   модерации на старте и не ломает обещание «фото не публикуются» (фото не публикуем — публикуем факт
   «здесь находили базальт»).
2. **B (Верификация)** — когда есть хотя бы несколько десятков активных: даёт данные для дообучения и
   осмысленное взаимодействие. Тут же вводим opt-in публикацию фото — но с понятной целью («помочь определить»),
   а не «показать всем».
3. **A (Лента)** — только если после C и B видно, что людям не хватает именно социального потока. К этому
   моменту уже будет и модерация, и репутация, и opt-in — то есть лента станет дешёвой надстройкой, а не
   стройкой с нуля.

Метрика, по которой решать про A: доля пользователей, открывающих страницу места или очередь верификации
чаще одного раза в неделю. Если она низкая — лента проблему не решит, проблема в ядре.

## Что нужно от тебя, чтобы двигаться

1. Согласие на изменение копии онбординга и на модель «публикация только по opt-in».
2. Выбор: идём по C → B → A или ты хочешь ленту сразу (тогда план другой, и первым делом — модерация).
3. Решение по 3b (подсветка всех посещённых ячеек, а не только закрытых) — оно частично пересекается с C.
