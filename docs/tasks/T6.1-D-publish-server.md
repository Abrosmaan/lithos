Статус: **готово** · 2026-09-10 · ветка `design-refresh` · поток D (T6.0-fixes-and-social.md §2, §4.1)

- `apps/mobile/src/lib/publish.ts` — клиентский слой поверх схемы.

## Схема

- `lithos.cards.published boolean not null default false`, `published_at timestamptz`; частичный индекс
  `cards_published_idx (published, published_at desc) where published`.
- Представление `lithos.public_finds` (выполняется с правами владельца — `postgres`, поэтому видит карточки
  всех пользователей в обход `cards_own`, но отдаёт только перечисленные колонки):
  `id, rock_class, tier, score, lore, name, user_name, cell_id, created_at, published_at, author_name`.
  `where c.published and not c.hidden and c.verification <> 'pending_review'`.
  `grant select … to authenticated` (не `anon`, не `public`).
- RPC `lithos.publish_card(p_card_id, p_published)` — security definer, проверяет владельца (`user_id =
  current_user_id()`), запрещает публикацию `hidden` (родитель после раскола) и `pending_review`, ставит/снимает
  `published`/`published_at`. Возвращает обновлённую строку `lithos.cards`.
- RPC `lithos.public_photo_path(p_card_id)` — путь лицевого фото (`is_primary`) опубликованной карточки.
- Политика `storage.objects` **"lithos photos select public"** — доп. к «select own» (0002): `select` разрешён
  для объекта, если он — лицевое фото (`is_primary`) какой-то опубликованной/невидимой/непроверяющейся
  карточки. Обе (RPC-путь и storage-политика) нужны вместе — см. «Фото» ниже.
- `lithos.reports(id, card_id, reporter_id, reason ≤500, created_at)`, `unique(card_id, reporter_id)`. RLS
  включён, политик нет (как `lithos.limits`) — читают только definer-функции и `service_role`.
- RPC `lithos.report_card(p_card_id, p_reason)` — вставляет жалобу (`on conflict` → `already_reported`),
  при достижении порога снимает публикацию (`published=false`, **не трогая `hidden`** — то поле означает
  «скрыто от владельца после раскола», а не «снято с витрины по жалобам», путать нельзя).

## Что видно наружу / что нет (сверено с data-map.md и §2.1)

Наружу: id, порода, тир, score, лор, имена (карточки и владельца), `cell_id`, даты. **Не наружу**: `lat/lng`
(в `public_finds` их нет и быть не может — это единственная проверяемая тестом инвариант), `scan_id` (сознательно
не включён — не расширяем поверхность представления), `hidden`/`verification`-детали, весь остальной `lithos.cards`
(прямого grant на таблицу для чужих строк нет — `select`/`update` для `authenticated` ограничены RLS `cards_own`;
`public_finds` обходит это только для явно перечисленных колонок явно опубликованных строк).

## Фото: почему два механизма, а не один

Задание просило политику на `storage.objects` (сделано) и предлагало RPC `public_photo_path` только как
запасной вариант «если политикой не выразить». По факту нужны **оба**, а не «или»: `public_finds` не содержит
`scan_id`/путь к файлу (минимальная поверхность), поэтому клиенту нечем спросить `scan_photos` напрямую —
RPC даёт путь по `card_id`. А сам `createSignedUrl` в любом случае идёт через Storage REST API, который
проверяет RLS на `storage.objects` перед подписью — без политики подпись не выдастся, даже зная путь.
Т.е. RPC решает «как узнать путь», политика — «можно ли этот путь подписать»; они не взаимозаменяемы.

## Решения (что решил сам, без владельца)

- **Порог автоскрытия жалобами = 3.** Захардкожен константой прямо в `report_card` (`v_threshold constant int
  := 3`), не вынесен в `packages/shared` — это не балансовое число score/тиров (правило CLAUDE.md про
  `score.ts` про них), а серверный порог модерации без клиентской логики вокруг значения. Изменить — новая
  миграция, поменять число в функции.
- **По жалобам карточка снимается с публикации, но не помечается `hidden`.** `hidden` — про раскол
  (родитель после split), смешивать с модерацией не стал: иначе жалобы начали бы прятать карточку и из
  собственной коллекции владельца, чего в тексте задачи не просили.
- **`published_at` обнуляется при снятии** (ручном и по порогу жалоб), а не хранит историю последней
  публикации — при повторной публикации ставится текущий `now()`. Если понадобится история публикаций —
  отдельная таблица, не в счёт этой задачи.
- **`reportCard` возвращает `'reported' | 'already_reported'`**, а не бросает ошибку на повтор — это
  сознательно (нужно два разных текста на экране, consent-copy.md §7), решение, какой текст показать —
  за экраном (поток E).
- **`author_name` может быть `null`** (если `display_name` не задан) — подстановку «Без имени» делает экран
  (data-map.md/§2.1 отдают это UI, не серверу).
- Не стал добавлять `scan_id` в `public_finds` ради «удобства» клиента — специально держал поверхность узкой
  (см. «Фото» выше); это мой выбор в пользу принципа «меньше поверхность» из T6.0 §2.2.

## Правки после ревью (оркестратор, 2026-09-10)

Ревью вернуло NEEDS_WORK: один блокер, два major, три minor. Что сделано.

### Блокер — исправлен: анонимный доступ к путям фото
`0007` выдала функции витрины, но не отозвала право на вызов у роли `PUBLIC`, которое Postgres добавляет
новой функции по умолчанию (в `0005` это учтено, здесь — нет). `lithos.public_photo_path` не проверяет
`current_user_id()`, поэтому вызывающий с одним лишь публичным anon-ключом, без сессии, мог получить
`storage_path` любой опубликованной карточки — а путь по формату `0002` содержит `user_id/scan_id` владельца.
Само фото оставалось закрыто (политика `storage.objects` выдана только `authenticated`), утекали идентификаторы.

Новая миграция **`0010_showcase_grants_hardening.sql`** (0007 применена, править её нельзя): `revoke all on
function ... from public` для `public_photo_path`, `publish_card` и `report_card` плюс явный `grant execute
... to authenticated`. Применена, проверено запросом `has_function_privilege`: для `anon` — `false`, для
`authenticated` — `true` по всем трём.

### Major «два механизма вместо одного» — оставлено, но это вопрос владельцу
Ревью право в том, что T6.0 §2.2 предписывал выбрать один вариант («RPC, возвращающий подписанный URL» —
меньше поверхность), а сделаны оба. Но вариант из плана в чистом SQL нереализуем: подписанный URL выдаёт
служба Storage по своему секрету, и функция Postgres его не создаёт — если только не класть секрет в базу,
что заметно хуже. То есть выбирать было не из чего: RPC отвечает на вопрос «какой путь», политика на
`storage.objects` — «можно ли этот путь подписать», одно без другого не работает.

Считаю посылку плана ошибочной, а реализацию — вынужденной. **Владельцу решать**, устраивает ли это; если
нет, альтернатива — отдавать путь колонкой самого `public_finds` и убрать RPC, но тогда `user_id` владельца
виден всем вошедшим сразу, а не по одной карточке за раз. Молча за владельца это не решалось: пункт вынесен
сюда и в финальный отчёт.

### Major «порог жалоб» — принято, число переехало в shared
Ревью справедливо сослалось на прецедент `lithos.limits` (0005): пороги поведения там уже живут в
`packages/shared` и сверяются с миграцией тестом. Порог автоскрытия — того же рода. Добавлена константа
`REPORT_AUTOHIDE_THRESHOLD` в `packages/shared/src/limits.ts` (с объяснением, почему SQL дублирует число) и
тест в `publish.test.ts`, который читает `v_threshold` из текста миграции 0007 и падает при расхождении.
Таблицу `lithos.limits` для одного значения не заводил — сид пришлось бы тянуть новой миграцией ради числа,
которое всё равно читается только внутри `report_card`.

### Minor — исправлено
- `decodeCursor` (`publish.ts`) проверяет обе части курсора по форме (timestamptz и uuid) и возвращает `null`
  на всё непохожее: чужой или испорченный курсор с запятой/скобкой больше не уезжает в фильтр `.or(...)`,
  где эти символы — синтаксис PostgREST. Страница в таком случае начинается сначала, а не падает. 4 теста.

### Minor — оставлено осознанно
- `publish_card` возвращает строку `lithos.cards` целиком. Это не утечка (данные самого вызывающего, и так
  доступные ему через `select`), но шире, чем нужно. Сужение меняет тип возврата, то есть `drop function` +
  новая миграция, ровно в тот момент, когда параллельный агент пишет экран поверх `setPublished`. Отложено,
  чтобы не ломать работу на ходу; хвост для следующей задачи.
- Тест-инвариант «нет координат» текстовый: ловит неосторожность (переименование, новую колонку), но не
  умышленный обход через join к другой таблице. Как единственная защита от неосторожности — приемлемо.
