# T6.1-E3 — профиль: подключение настроек, публикаций и старой витрины

Статус: **готово, гейты зелёные, не закоммичено**. 2026-09-10, ветка `design-refresh`. Финальный кусок потока E
(T6.0-fixes-and-social.md §2, §4.1), опирается на готовое от потоков D/E1/F.

## Что сделано

1. **Пять настроек подключены** (`ProfileScreen.tsx#onSettingPress`):
   - `privacyPolicy`/`termsOfUse` → `navigation.navigate('Policy', { doc: 'privacy' | 'terms' })` (как `openCard`
     уже делает для `Card` — композитная навигация таба пропускает root-маршруты без `getParent()`).
   - `training` → `onTrainingPress()`: включение сразу через `setTrainingOptIn(true)`, выключение — только
     после `Alert` с `TRAINING_OPT_OUT_DIALOG`. Оптимистичное обновление `profile.trainingOptIn` с откатом при
     ошибке (стиль `doPublish` из `CardScreen`), `trainingBusy` гейтит повторные тапы. Значение в строке —
     из `fetchProfile().trainingOptIn`, передаётся в `settingsRows({ trainingOptIn })`.
   - `serverWipe` → `Alert(SERVER_WIPE_DIALOG)` → `deleteServerData()`; во время запроса `serverWiping=true`
     блокирует остальные настройки (RPC + удаление файлов не мгновенно, врать бездействием нельзя — показана
     `Note` «Удаляем данные на сервере…»); по успеху `Alert(SERVER_WIPE_DONE)` и **только по OK** — сброс стека
     на `Welcome` (как `doWipe()`): пользователь не остаётся в интерфейсе с уже удалёнными, но ещё нарисованными
     карточками. По ошибке — `SERVER_WIPE_FAILED`, `serverWiping` снимается, экран остаётся как был (нечего
     скрывать: ничего не удалилось).
   - `publications` → toggle `showPublicationsInfo`, показывает `PUBLICATIONS_TEXT`/`PUBLICATIONS_EMPTY_TEXT`
     под списком настроек — ровно так, как описано в `settings.ts` («раскрывается тапом, как PRIVACY_TEXT»).

2. **Блок «Мои публикации»** заменил старую «Витрину»: список строится из `cards.published` (поле уже есть в
   `CardRow`/`CARD_COLUMNS` после E1) через `visible.filter(c => c.published)` — отдельного запроса не
   понадобилось, как и предполагала задача. Фото для плиток подтягиваются той же `fetchPrimaryPhotoUrls`, что
   и для редчайшей/самой далёкой (список «желаемых» scan_id в `load()` расширен публикациями вместо старых
   `showcaseIds`). Пусто → `PUBLICATIONS_EMPTY_TEXT`; есть публикации → грид + `SHOWCASE_PROFILE_FOOTNOTE`
   («Всё, что здесь лежит, видно другим пользователям», уже подготовлен потоком F в `lib/consent.ts`) + кнопка
   «Убрать все публикации».
   - Массовое снятие — `Promise.allSettled(setPublished(id, false))` по всем опубликованным разом. Оптимистично
     обновляет только реально успешные id (`okIds`), честный итог — через новую чистую функцию
     `summarizeBulkUnpublish(total, succeeded)` (`lib/publications.ts`): три исхода (полный успех, частичный,
     полный отказ), нигде не говорит «готово», если что-то не снялось. Диалог подтверждения — `UNPUBLISH_ALL_DIALOG`
     там же.

3. **Старая локальная витрина убрана из экрана.** `ProfileScreen` больше не читает `AsyncStorage` через
   `readShowcase`/`pruneShowcase` — реальность (сервер) и есть источник правды. В `lib/showcase.ts` удалены
   `writeShowcase`, `pruneShowcase`, `toggleShowcaseCard` — по всему `apps/mobile/src` проверено `grep`: на них
   больше никто не ссылался (не путать с `toggleShowcase` — его напрямую использует `lib/stats.test.ts`, вне
   границ задачи, поэтому оставлен и не переименован; `readShowcase`, `planShowcaseMigration`,
   `isShowcaseMigrationDone`/`markShowcaseMigrationDone`, `isPublishExplained`/`markPublishExplained` тоже
   оставлены — их использует `CardScreen.tsx`, чужой экран). Тест `showcase.test.ts` не трогал — он и не
   ссылался на удалённые функции.

4. **Новый модуль** `lib/publications.ts` (+ `publications.test.ts`, 5 кейсов): текст диалога массового снятия
   и `summarizeBulkUnpublish`. Чистые функции, без сети/AsyncStorage — сетевой вызов остаётся в `ProfileScreen`.

## Прочие хвосты

- Один и тот же короткий текст (`PUBLICATIONS_EMPTY_TEXT`) показывается в двух местах при отсутствии
  публикаций: и в самом блоке, и в раскрывающемся пояснении настройки. Решение сознательное (обе локации по
  смыслу верны для этого текста), но при желании можно сократить до одного места.
- `doServerWipe`/`setTraining` используют тот же паттерн отката, что и `CardScreen#doPublish` (оптимистичное
  обновление + откат при ошибке), но `ProfileScreen` не проверяет «экран ещё смонтирован» после `await` —
  как и было отмечено хвостом в T6.1-E1 для `CardScreen`; безвредно на React 18, но стоит унифицировать при
  следующем большом заходе на файл.
