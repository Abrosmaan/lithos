# T2.1 — Воркер: конвейер S0–S4 (+ серверная часть раскола T2.3)

Статус: **готово; ревью 1 NEEDS_WORK → исправлено (см. «Ревью»); end-to-end на golden set (20 фото, доля S3 ≤ 25 %) — ждёт T2.4** · 2026-09-07

## Что сделано

`apps/worker/src/index.ts` — hello-цикл заменён на конвейер. Очереди читаются в порядке
`scan_interactive → scan_dispute → scan_batch` (`pgmq.read`, lease 60 с), lease продлевается heartbeat'ом
(`pgmq.set_vt`, каждые 20 с) пока идут ступени; после `read_ct > 3` сообщение уходит в DLQ (`pgmq.archive`);
цепочка дольше 90 с — воркер возвращается в цикл, обработка продолжается в фоне (до 2 одновременно), карточка
для клиента «в обработке» (`scans.stage` не `done`). Жёсткий дедлайн задачи 10 мин (`jobDeadlineMs`): heartbeat
прекращается, слот освобождается, результат зависшей задачи не подтверждается — сообщение возвращается по lease и
штатно доходит до DLQ. Один `scan_id` обрабатывается эксклюзивно (`pg_try_advisory_lock` на время `runScan`; занят →
`deferred`, сообщение откладывается на 10 с без ack). Пул pg: `connectionTimeoutMillis` 10 с, `statement_timeout` 60 с.

Сигнатуры pgmq проверены в БД: `read(queue_name text, vt integer, qty integer, conditional jsonb)`,
`set_vt(queue_name text, msg_id bigint, vt integer)`, `archive(queue_name text, msg_id bigint)`,
`delete(queue_name text, msg_id bigint)`, `send(queue_name text, msg jsonb)`.

### Ступени

- **S0.** Фото из Storage (параллельно) → `normalizeImage` → резкость + pHash; `scan_photos.phash` пишется, если пусто.
  Битое/пропавшее фото среди нескольких пропускается (warn в лог); нет ни одного годного → `failed/photo_unavailable`.
  `scans.stage: preflight → gate`. Дедуп: pHash сканов того же пользователя за 24 ч, `stage='done'`, с не скрытой
  карточкой, не расколов; Хэмминг ≤ 6 по любой паре фото → копия карточки (те же поля, новая строка, `user_name` не
  копируется), `scan_results.preflight = {phash_hit, source_scan_id, source_card_id, distance}`, `provider='phash_cache'`,
  cost 0, `scans.stage='done'`, модели не вызываются, дневник не трогается. Дедуп пропускается для расколов и
  disputes.
- **S1 Gate.** Фото: `is_primary` от клиента, иначе максимум нашей резкости. `is_rock=false → not_rock`;
  `quality≠ok → blurry|dark|too_far|screen_photo`. Результат пишется в `scan_results.gate`, `scans.stage='failed'`,
  `scans.error=<код>` в одной транзакции; карточка не создаётся. `screen_photo` в `scans.error` и есть пометка
  антифрода (сырой ответ — в `scan_results`). `multiple_objects=true` один **не останавливает** (см. «Решения»).
- **S2 Main.** До 3 фото в порядке `storage_path`, `GeoContext` (`getGeoContext(lat, lng)`, запрашивается
  параллельно с Gate; без координат — `null`), `user_tests`, `userLanguage='ru'`, `scaleObject='coin or finger'` при
  `has_scale_photo`. Раскол: `lat/lng` и `user_tests` — от родительской карточки / её скана; после ответа
  `surface='fresh_split'` принудительно (`applyOverrides`, применяется на каждом replay, в `raw_json` — ответ модели как есть).
- **S3 Escalation.** Триггеры — `escalationTriggers(result, internal_tier, geo)` из shared + `'dispute'` для очереди
  `scan_dispute`. При `usedFallback=true` на Main — S3 пропускается (`meta.escalation='skipped_fallback'`). Если
  триггеры есть: **сначала карточка по S2** (`upsertCard`, `scans.stage='escalation'`, `meta.escalation='pending'`) —
  клиент показывает результат с пометкой «уточняем»; затем `callModel('escalation', priorResult)` → карточка
  перезаписывается (upsert по `scan_id`, тот же `cards.id`). Оба провайдера S3 отказали (`LlmUnavailableError`) →
  финал по S2, `provisional=true`, `meta.escalation='failed'`, скан `done` (скан не теряется, §7 «Деградация»).
- **S4 Rules.** `computeScore(result, geo, tests)`; `usedFallback` → `clampTier(tier, FALLBACK_MAX_TIER)` +
  `provisional=true` (score не режется, `tier_clamped=true`); `geo_anomaly` → `verification='pending_review'`;
  `inclusions` — только прошедшие порог (`scoredInclusions`); `name` автоген; раскол → `state='opened'`,
  `parent_card_id`, родитель `hidden=true`, `score_breakdown.split_from/split_delta`; дневник `(user_id, cell_id)`:
  `expected = expected_rocks` из гео (перезаписывается), `found ∪= rock_class` (кроме `unknown*`); `scans.stage='done'`.
  `scans.cost_usd = sum(scan_results.cost_usd)` пересчитывается при каждой записи ступени (идемпотентно).
- **Ошибки.** `ScanRejected` / `PhotoUnavailableError` → `failed` с кодом. Любая другая ошибка (БД, Main недоступен)
  — наружу: сообщение не подтверждается, `set_vt` 10 с, следующее чтение = повтор с идемпотентностью; при
  `read_ct > 3` — `archive` + `dlqScan`: карточки нет → `failed/dlq`; предварительная карточка уже есть → `done`,
  карточка `provisional=true`. В `scans.error` — только коды, текст провайдера никогда.
- **Логи.** На каждую ступень `pipeline stage {scan_id, stage, ms, cached, provider, used_fallback, cost_usd, next}`;
  `pipeline done {scan_id, ms, card_id, escalation, triggers}`; `scan processed {queue, msg_id, read_ct, status, reason, ms}`.
  Вызовы моделей логирует `callModel` (T1.3).

## Контракт для клиента (T2.2 / T2.3)

Realtime: подписка на `lithos.scans` и `lithos.cards` по `scan_id` (обе в публикации, T0.1).

**`scans.stage`** (что сейчас делает воркер) и **`scans.error`**:

| stage | смысл для клиента |
|---|---|
| `preflight` | ещё не взят воркером |
| `gate` | фото скачаны, идёт фильтр |
| `main` | Gate пройден, идёт основной вердикт |
| `rules` | Main готов, считаем карточку (миг) |
| `escalation` | **карточка уже есть** (Realtime insert в `cards`) — показать её с пометкой «уточняем» |
| `done` | финал; карточка окончательная (если `cards.provisional=false`) |
| `failed` | отказ, `scans.error` = код: `not_rock`, `blurry`, `dark`, `too_far`, `screen_photo`, `photo_unavailable` (фото не открылось — переснять), `parent_not_found` (раскол без родителя), `dlq` (не смогли обработать — «попробуйте позже»). Код `multiple_objects` зарезервирован, сейчас не выдаётся. |

`scans.cost_usd`, `provider`, `prompt_version` — служебные, обновляются после каждой ступени.

**`cards`** (одна строка на `scan_id`, `cards.id` стабилен между предварительной и финальной версией):

- `rock_class` (enum shared), `tier` / `score` — **null, если скана без гео** (spec §4.1; миграция 0004);
- `score_breakdown` = `{ shape, place, composition, quality }` из `computeScore` + `wanderer`, `geo_anomaly`, `has_geo`,
  `internal_score`, `internal_tier` (не показывать при `!has_geo`), `tier_clamped`, при расколе `split_from` (id
  родителя) и `split_delta` (`score − score родителя`, null если у кого-то нет score), при pHash-копии `phash_hit`, и
  `meta`: `{ triggers[], escalation: 'none'|'pending'|'done'|'skipped_fallback'|'failed', fallback, provider,
  prompt_version, geo_source, split_recommendation: {recommended, reason} (модель И правила, для кнопки «Расколоть»),
  alternatives[], confidence, flags[], revision_note }`;
- `inclusions` = `[{mineral, extent, confidence, location, evidence}]` — только ≥ 0.6;
- `shape` = `{tags[], natural_hole, recognizable_silhouette, surface}`;
- `lore`, `name` (автоген; `user_name` — пользовательское, воркер не трогает);
- `state` `closed|opened`, `parent_card_id`, `verification` `ai|pending_review` (гео-аномалия: тир показывать как «?»),
  `provisional` (fallback-провайдер или S3 недоступен → «предварительно»), `hidden` (родитель после раскола —
  не показывать в коллекции), `cell_id` (geohash-6), `lat`, `lng` (у раскола — родительские).

**Раскол (T2.3):** клиент создаёт скан с `parent_card_id`, гео/тесты можно не передавать; после `done` —
новая карточка `opened`, родитель `hidden=true`; дельта — `score_breakdown.split_delta`.

**Оспорить:** `enqueue_scan(scan_id, 'scan_dispute')` на done-скане → `scans.stage='escalation'` → S3 (Opus) →
карточка обновляется; повторный dispute того же скана — no-op (S3 уже есть в `scan_results`, в БД ничего не меняется —
клиенту сигнала нет, см. «Не сделано»). Если фото скана уже недоступны — карточка и `done` не трогаются. Лимит 3/день — T3.4.

**Сверка с T2.2 (docs/tasks/T2.2.md, `apps/mobile/src/lib/{card-types,history}.ts`) — расхождения, править на стороне клиента:**
1. Клиент парсит `scan_results.raw_json` напрямую `ScanResultSchema` (история версий, рекомендация раскола). У воркера
   `raw_json = {result, meta}` → парсить `raw_json.result`. Рекомендация раскола дублируется в
   `cards.score_breakdown.meta.split_recommendation` — можно брать оттуда без `scan_results`.
2. Коды `photo_unavailable`, `parent_not_found` отсутствуют в клиентском `SCAN_ERROR_CODES` → показываются как `dlq`
   («попробуйте позже»); для `photo_unavailable` правильнее «переснять».
3. `cards.shape.surface` есть (клиент это предполагал); `cards.score/tier` могут быть `null` (миграция 0004 применена).

## Решения

- **Инжекция зависимостей вместо `vi.mock`.** `createPipeline({repo, photos, callModel, getGeoContext, log, now})`:
  unit-тесты используют in-memory `FakeRepo` с той же семантикой транзакций, боевой код — `PgPipelineRepo` + supabase-js.
  Тест (а) «убить после ответа Main до записи» трактован как «после записи `scan_results.main`, до карточки»: если
  процесс умирает до записи, ответ потерян и повторная оплата неизбежна — поэтому запись ступени идёт сразу после
  ответа, до любых дальнейших шагов, в одной транзакции со `scans.stage`.
- **Форма `scan_results.raw_json`:** `{result, meta:{used_fallback, fallback_reason, repeated, attempts}}` — на replay
  нужно знать, что результат пришёл через fallback (иначе повтор снял бы «предварительно»). `result` — ответ модели
  как есть (в т.ч. до override `fresh_split`).
- **`scans.stage` = «что делает воркер»**, промежуточный ответ — `stage='escalation'` при уже существующей карточке
  (без новой колонки `cards.stage_hint`); дополнительно `score_breakdown.meta.escalation='pending'` в самой карточке.
- **S3 недоступен → финал по S2 как `provisional`**, а не retry через очередь: пользователь уже видит карточку, ждать
  минуты ради Opus бессмысленно; переанализ через batch — вне прототипа.
- **DLQ с предварительной карточкой → `done` + `provisional`,** а не `failed`: у клиента карточка на экране, «ошибка»
  после неё хуже «предварительно».
- **`multiple_objects` не останавливает:** ai-pipeline §3 S1 не даёт такого решения (стоп только по `is_rock`,
  `quality`, `screen_photo`), dev-plan T2.2 не имеет экрана отказа для него. Код оставлен в `SCAN_ERROR_CODES` на будущее.
- **Surface hint для раскола не передаётся в промпт** — `CallModelInput` (T1.3) не имеет такого поля, а `llm/**` вне
  границ задачи; `surface='fresh_split'` применяется после ответа (spec/dev-plan T2.3 требуют именно пометку).
  Предложение для `llm`: `CallModelInput.surfaceHint?: Surface` → строка в user-сообщении Main.
- **pHash-копия:** `lat/lng/cell_id` — исходной карточки (гео не запрашивается, score считать не по чему);
  `user_name` не копируется; исходники-расколы и скрытые карточки не считаются.
- **Гео параллельно с Gate** — `getGeoContext` не бросает (T1.2), выигрываем ~1–2 с на первом скане в ячейке.
- **Изображение нормализуется на воркере** (rotate + ≤ 1024 px + q=85) даже если клиент уже сжал — защита бюджета
  токенов от чужих клиентов/старых версий; резкость и pHash считаются на нормализованной копии.
- **Timeout цепочки** реализован в consumer через race: воркер продолжает читать очередь (inflight ≤ 2), задача
  дорабатывает в фоне под heartbeat lease; на shutdown — `drain()`.
- **Fallback-`no_api_key`** (Google без ключа) — не «предварительно» (T1.3): в интеграции Gate прошёл через Anthropic с
  `used_fallback=false`.
- **Advisory lock на scan_id** (ревью m5): истёкший lease при живой задаче / повторный `enqueue_scan` / dispute во время
  интерактивной обработки — второй процесс получает `deferred` и не платит за ту же ступень. Lock сессионный на выделенном
  соединении пула (max 4, inflight ≤ 2), снимается в `finally`; при ошибке unlock соединение выбрасывается из пула.
- **Жёсткий дедлайн 10 мин** (ревью M2) считается по worst-case провайдерного слоя (3 ступени × 4 попытки × 2 провайдера)
  — прерывать `runScan` через AbortSignal нельзя без правки `llm/**`, поэтому зависшая задача только отпускается
  (без ack), а очередь и DLQ делают остальное.
- **Poison `raw_json`** (сохранённый результат не по текущей схеме) → ошибка → 3 чтения → DLQ. Осознанно: смена
  `ScanResultSchema` — событие golden-set-уровня (dev-plan §5.8), и видимый DLQ лучше тихого повторного вызова модели с
  `ON CONFLICT DO NOTHING`, который оставил бы старую строку.

## Ревью

Ревью 1 (NEEDS_WORK) → исправлено: **M1** Storage — таймаут на fetch + retry (+ параллельная загрузка фото, битое из
нескольких пропускается); **M2** жёсткий дедлайн задачи (heartbeat прекращается, слот освобождается, `abandoned` без
ack), таймауты пула pg, `drain()` с таймаутом; **m1** geohash убран из имени; **m2** `scaleObject` не утверждает «фото 1»;
**m3** одно битое фото не роняет скан; **m4** dispute с пропавшими фото не понижает `done`; **m5** advisory lock на
`scan_id` (+ `deferred` в consumer); **m6** diary-merge / upsert / lock / dlq прогнаны на реальной БД; **m7** тесты на
heartbeat и дедлайн; **m9** мёртвый `config.leaseSeconds` удалён. **M3** — приёмка на golden set остаётся открытой до T2.4
(ниже). Не взято (зафиксировано ниже): m8, m10, m11 (решение выше), m12, m13.
