# T7.3-A — точные координаты в витрине: сервер

Статус: **готово** · 2026-10-03 · ветка `design-refresh` · поток A

Решение владельца (2026-10-03, отменяет прежнее из T6.0-fixes-and-social.md §2.1–2.2): опубликованная
находка показывается на карте точными координатами, как в iNaturalist, а не центром ячейки geohash-6.
Цена принята осознанно: точное место находки видно всем, для уже опубликованного это необратимо.
На момент работы опубликованных карточек в базе 0 — задним числом ничего не раскрыто (проверено).

## Что сделано

- `supabase/migrations/0016_public_exact_coords.sql` — `lithos.public_finds` пересоздано (`drop view` +
  `create view`, не `create or replace`: новые колонки нужны рядом с `cell_id`, а Postgres разрешает
  добавлять колонки через "or replace" только в конец списка). Шапка файла подробно объясняет смену
  модели, кем и когда принята и чем оплачена — это сознательное решение, не недосмотр.
- Остальной набор колонок, условия отбора (`published`/`not hidden`/`verification<>pending_review`),
  RPC (`publish_card`, `report_card`, `public_photo_path`) и политика `storage.objects` — не трогал.
- Грант `select` на представление выдан явно заново (дроп снимает прежние права) — только `authenticated`.
- `apps/mobile/src/lib/publish.ts`: `PublicFindRow` получил `lat?`/`lng?` (точные координаты из вида).
  `center` (через `cellCenter(cell_id)`) оставлен как есть — его читают `lib/public-map.ts` и
  `PublicFindScreen.tsx` (вне границ задачи), и `cell_id` всё ещё нужен дневнику места. `lat`/`lng` сделаны
  опциональными в типе (а не `number | null`) намеренно: `public-map.test.ts` (тоже вне границ) строит
  фикстуры без этих полей — обязательность сломала бы typecheck в чужом файле.
- `publish.test.ts`: инвариант «нет lat/lng» заменён на обратный — «lat/lng есть намеренно» со ссылкой на
  решение от 2026-10-03; источник для тестов колонок/грантов переключён на 0016 (0007 больше не описывает
  действующий вид представления). Добавлены разбор строки с координатами и без (включая битые lat/lng).

## Применено и проверено на живой базе

`pnpm db:migrate` → `apply 0016_public_exact_coords.sql`; `pnpm db:migrate:status` — все 16 применены.
Разовый скрипт (временный, удалён после проверки, без вывода строки подключения):
колонки `public_finds` = `id, rock_class, tier, score, lore, name, user_name, cell_id, lat, lng, created_at,
published_at, author_name`; `has_table_privilege`: `anon`=false, `public`=false, `authenticated`=true;
`select count(*) from lithos.cards where published` = 0; данные не менял.

## Гейты

`pnpm typecheck`, `pnpm lint` — зелёные. `pnpm test` — зелёный для моих файлов (`publish.test.ts` 17/17,
`public-map.test.ts` 5/5 не задет); один непричастный провал — `src/legal/index.test.ts` (копия политики в
бандле разошлась с `docs/legal/privacy-policy.ru.md`), это правит параллельный агент по compliance-потоку,
я `docs/legal/**` не трогал.

## Что осталось клиенту/документам (вне этой задачи)

`lib/public-map.ts` сейчас строит точки чужих находок из `center` (центр ячейки), а не из новых точных
`lat`/`lng` — переключить на точные координаты предстоит потоку, владеющему этим файлом. Экраны (карта,
карточка чужой находки) и `docs/legal/**` — тоже отдельные потоки.
