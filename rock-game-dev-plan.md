# Lithos — план разработки прототипа

Версия 0.1 · 7 сентября 2026 · основан на rock-game-spec.md и rock-game-ai-pipeline.md

Документ написан как задание для AI-исполнителя (Claude Code / субагенты). Каждая задача имеет вход, выход, критерий приёмки и файл-артефакт, куда фиксируется результат. Задачи внутри волны независимы и запускаются параллельно, 3–5 агентов за раз.

---

## 0. Что считается рабочим прототипом

Demo-сценарий, который должен проходить целиком на реальном телефоне:

1. Открыть приложение без регистрации → камера.
2. Сфотографировать камень на пляже (1–3 фото) → через ≤ 5 с экран результата: порода, тир, три факта, лор.
3. Нажать «Расколоть и пересканировать» → второй скан → карточка обновляется, score меняется.
4. Открыть коллекцию → карточка на месте, дневник локации показывает закрытые/незакрытые позиции.
5. Открыть карту → точка скана.
6. Сфотографировать телефон с экрана / чашку → отказ с понятным сообщением.
7. Отключить ключ основного провайдера → скан всё равно проходит через fallback с пометкой «предварительно».

Всё остальное (обмен, верификация, grading, NFT, рынок, подписка) — вне прототипа.

## 1. Стек

Выбор — по критерию «меньше всего кода и инфраструктуры между фото и карточкой».

| Слой | Решение | Почему |
|---|---|---|
| Мобильный клиент | Expo (React Native) + expo-camera + expo-location | Один код на iOS/Android, камера и гео из коробки, EAS-сборка без Xcode на машине |
| Бэкенд/БД/хранилище | Supabase (Postgres + Storage + Auth anon + Realtime) | Всё в одном, RLS, Realtime для push результата в клиент |
| Очередь | pgmq (расширение Supabase) | Очередь в той же БД, без Redis; три очереди по приоритету |
| Воркер | Node 20 + TypeScript, один процесс на Fly.io/Railway | Читает pgmq, вызывает модели, пишет результат |
| Модели | Vercel AI SDK (`ai` + `@ai-sdk/anthropic` + `@ai-sdk/google`) с zod-схемой | Structured output и смена провайдера конфигом |
| Геослой | Macrostrat API (`/api/v2/geologic_units/map`) с кэшем в Postgres | Глобальная литология по координатам, бесплатно |
| pHash | `sharp` + `imghash` в воркере | Дедупликация фото |
| Карта | react-native-maps / MapLibre | Точки сканов |
| Монорепо | pnpm workspaces: `apps/mobile`, `apps/worker`, `packages/shared` | Схема и enum'ы общие для клиента и воркера |

Не используется в прототипе: собственный классификатор, Redis, Kafka, микросервисы, блокчейн.

## 2. Структура репозитория

```
lithos/
  apps/
    mobile/            Expo-приложение
    worker/            воркер очереди
  packages/
    shared/            zod-схемы, enum'ы, таблицы score, типы
  supabase/
    migrations/        SQL
    seed/              golden set, enum-справочники
  docs/                эти три документа + артефакты задач
    tasks/             по одному .md на задачу: результат, решения, нерешённое
  .env.example
  README.md            как поднять локально за 15 минут
```

Правило для агентов: результат каждой задачи записывается в `docs/tasks/<ID>.md` до того, как агент завершает работу. Формат: что сделано, какие файлы, как проверить, что не сделано и почему.

## 3. Данные

### Таблицы (Supabase)

```sql
users        id, created_at, device_id, display_name
scans        id (uuid = idempotency key), user_id, lat, lng, accuracy_m,
             created_at, stage (preflight|gate|main|escalation|rules|done|failed),
             attempt, provider, prompt_version, cost_usd, error
scan_photos  id, scan_id, storage_path, phash, is_primary, width, height
scan_results scan_id, stage, model, raw_json, created_at   -- один ряд на ступень
cards        id, scan_id, user_id, rock_class, tier, score, score_breakdown jsonb,
             inclusions jsonb, shape jsonb, lore, state (closed|opened),
             parent_card_id (для раскола), verification (ai|community|expert)
geo_cache    cell_id (geohash 6), macrostrat_json, expected_rocks jsonb,
             wanderers jsonb, fetched_at
diary        user_id, cell_id, expected jsonb, found jsonb
```

### Очереди pgmq
`scan_interactive`, `scan_dispute`, `scan_batch`. Воркер читает в этом порядке.

### Enum'ы (packages/shared/enums.ts)
- `RockClass` — ~60 значений + `unknown_igneous|sedimentary|metamorphic|unknown`
- `Mineral` — ~40
- `ShapeTag` — 12
- `Extent` — `traces|noticeable|dominant`
- `Surface` — `weathered|fresh_split|polished|coated`

Источник для списков — §5 пайплайна; агент, который их пишет, обязан сверить с mindat-номенклатурой и зафиксировать в артефакте, что выкинул и почему.

## 4. Волны задач

Каждая волна — до 5 параллельных агентов. Следующая волна стартует, когда все артефакты волны записаны и приёмка пройдена.

### Волна 0 — каркас (1 агент, последовательно)

**T0.1 Монорепо и окружение**
- Вход: этот документ.
- Выход: pnpm-монорепо, Expo-приложение с пустым экраном камеры, воркер с `hello`-циклом чтения pgmq, Supabase-проект с миграциями из §3, `.env.example`, README с запуском.
- Приёмка: `pnpm dev` поднимает всё локально; Expo Go показывает камеру; воркер логирует пустую очередь.
- Артефакт: `docs/tasks/T0.1.md`.

### Волна 1 — фундамент (4 агента параллельно)

**T1.1 Shared: схемы и таблицы score**
- Вход: пайплайн §5, ТЗ §6.
- Выход: `packages/shared`: zod-схема `ScanResult`, enum'ы, `computeScore(result, geoContext, userTests) → {score, tier, breakdown}` строго по таблицам ТЗ §6, включая порог confidence 0.6, множители и потолки слоёв.
- Приёмка: unit-тесты на 15 кейсов (обычный базальт → Common; куриный бог → +20; пемза на побережье → «странник» +20; включение с confidence 0.55 → не засчитано; и т.д.). Ни одно число score не берётся из confidence напрямую.
- Артефакт: `docs/tasks/T1.1.md`.

**T1.2 Геоконтекст**
- Вход: пайплайн §3 (S2), Macrostrat API.
- Выход: `apps/worker/src/geo.ts`: `getGeoContext(lat, lng)` → кэш по geohash-6 (30 дней) → Macrostrat → нормализация в `{expected_rocks[], age_range, setting, wanderers[]}`. Таблица `wanderers` по типу местности: побережье → drift pumice; широты > 45° → glacial erratic; русло → upstream transport.
- Приёмка: для 5 контрольных точек (Гонио, Дорсет, Аризона, Байкал, Исландия) возвращает осмысленный список ожидаемых пород; повторный вызов не ходит в API.
- Артефакт: `docs/tasks/T1.2.md`.

**T1.3 Провайдерный слой**
- Вход: пайплайн §2, §2a, §6, §7.
- Выход: `apps/worker/src/llm/`: `callModel(stage, input) → ScanResult` через Vercel AI SDK; провайдер и модель каждой ступени — из `config.ts`; промпты из пайплайна §6 в файлах `prompts/gate.ts`, `prompts/main.ts`, `prompts/escalation.ts` с `PROMPT_VERSION`; structured output по zod; retry 3× с backoff и jitter на 429/5xx/timeout; один repair-вызов на невалидную схему; circuit breaker на провайдера (25 % ошибок за 60 с → 2 мин закрыт); fallback на второго провайдера; учёт стоимости по токенам в `cost_usd`.
- Приёмка: тест с мок-провайдером: 429 → 3 ретрая → успех; 5 ошибок подряд → breaker открыт → вызов ушёл в fallback; невалидный JSON → repair → валидный. Реальный вызов на 3 фото из golden set возвращает валидную схему на обоих провайдерах.
- Артефакт: `docs/tasks/T1.3.md`.

**T1.4 Клиент: камера и загрузка**
- Вход: ТЗ §4.1, §12.
- Выход: экраны Camera → Review (до 3 фото, подсказка «одно с монетой/пальцем», три кнопки веса, три кнопки царапины, мокрый/сухой) → загрузка в Supabase Storage с ресайзом до 1024 px и blur-детектом на клиенте (отказ до отправки) → создание записи `scans` с `scan_id` = uuid v5(device_id + timestamp) → постановка в `scan_interactive` через RPC.
- Приёмка: на телефоне фото уходит в Storage, запись в `scans` со stage=`preflight`, сообщение в очереди.
- Артефакт: `docs/tasks/T1.4.md`.

### Волна 2 — конвейер (4 агента)

**T2.1 Воркер: конвейер S0–S4**
- Вход: T1.1–T1.3, пайплайн §3, §4.
- Выход: `apps/worker/src/pipeline.ts`: чтение очереди с lease 60 с; для каждой ступени — проверка `scan_results` на уже готовый результат (идемпотентность), вызов, запись; pHash-дедуп против сканов пользователя за 24 ч (Хэмминг ≤ 6 → копия результата, без вызова модели); Gate → стоп по `is_rock=false|quality≠ok|screen_photo`; Main; триггеры Escalation ровно по §3 S3; Rules через `computeScore`; запись `cards`; Realtime-уведомление клиента. Таймаут цепочки 90 с → карточка «в обработке», продолжение в фоне. DLQ после исчерпания попыток.
- Приёмка: интеграционный тест: убить воркер после ответа Main и до записи → перезапуск → Main не вызывается повторно (по логу стоимости). 20 фото из golden set проходят end-to-end, доля Escalation ≤ 25 % на этом наборе.
- Артефакт: `docs/tasks/T2.1.md`.

**T2.2 Клиент: результат и карточка**
- Вход: ТЗ §4.3, §5.
- Выход: экран Result (подписка на Realtime по `scan_id`; показ результата Main сразу с пометкой «уточняем», обновление после Escalation; тир, три факта, лор, кнопка «В коллекцию», кнопка «Расколоть и пересканировать» если `split_recommendation.recommended`); экран Card (все поля §5, breakdown score раскрывается по тапу, история версий). Экраны отказа для `not_rock / blurry / dark / too_far / screen_photo` с конкретной подсказкой.
- Приёмка: время от завершения загрузки до первого экрана результата ≤ 5 с на тестовом наборе при работающем Sonnet/Flash.
- Артефакт: `docs/tasks/T2.2.md`.

**T2.3 Раскол**
- Вход: ТЗ §7.
- Выход: экран безопасности (один раз, нельзя пропустить при первом расколе); поток «Расколоть» → новая съёмка → скан с `parent_card_id`; воркер при `parent_card_id` использует гео и user_tests родителя, помечает `surface=fresh_split`, после Rules — карточка `state=opened`, родительская карточка скрывается с пометкой «была раскрыта», score пересчитан, дельта показана.
- Приёмка: раскол на реальном камне: закрытая карточка исчезает из коллекции, открытая появляется с изменённым score и ссылкой на историю.
- Артефакт: `docs/tasks/T2.3.md`.

**T2.4 Golden set v0**
- Вход: пайплайн §9.
- Выход: `supabase/seed/golden/` — 60 фото (стартовый объём, не 300) с разметкой: 4 типа геологии по 12 + 12 ловушек (слюда/пирит, хлорит/малахит, бетон/известняк, стекло/кварц); источники — Kaggle-датасеты из переписки + собственные пляжные фото; файл `labels.json`; скрипт `pnpm eval` — прогон через провайдерный слой, отчёт: top-1/top-2 точность, precision включений при ≥ 0.6, доля уверенных ошибок (≥ 0.8 и неверно), стоимость на скан, латентность — по каждой модели каждой ступени.
- Приёмка: `pnpm eval` выдаёт таблицу для Haiku/Flash-Lite, Sonnet/Flash, Opus/Pro. Результат — в артефакт с рекомендацией по стеку.
- Артефакт: `docs/tasks/T2.4.md` — это же и есть решение по провайдеру.

### Волна 3 — игра (4 агента)

**T3.1 Коллекция и дневник**
- Вход: ТЗ §8.
- Выход: экран Collection (сетка карточек, фильтр по тиру, сортировка); экран Diary для текущей geohash-ячейки: `expected` из геоконтекста, `found` — по карточкам пользователя в ячейке; прогресс; значок при 100 %.
- Приёмка: после 3 сканов в одной точке дневник показывает 3 закрытые позиции из N.
- Артефакт: `docs/tasks/T3.1.md`.

**T3.2 Карта**
- Вход: ТЗ §8.
- Выход: экран Map: точки сканов пользователя с цветом тира; тап → карточка; ячейки с заполненным дневником подсвечены.
- Приёмка: точки соответствуют координатам сканов; работает офлайн для уже загруженных точек.
- Артефакт: `docs/tasks/T3.2.md`.

**T3.3 Профиль и статистика**
- Вход: ТЗ §8, §12.
- Выход: экран Profile: сканов, распределение по тирам, редчайшая карточка, самая далёкая находка; витрина до 12 карточек (локальная, без шеринга); anon-auth Supabase, имя редактируется.
- Приёмка: цифры совпадают с БД.
- Артефакт: `docs/tasks/T3.3.md`.

**T3.4 Антифрод и лимиты**
- Вход: пайплайн §4, §11 ТЗ.
- Выход: лимит 10 сканов/день на устройство, 20/день первые 24 ч; глобальный token bucket под RPM провайдера; гео-аномалия (тир ≥ Epic при `matches_local_geology=false` без механизма) → карточка `verification=pending_review`, тир показан как «?»; бюджетный предохранитель: дневной лимит USD в конфиге, 80 % → Escalation выключен, 100 % → очередь с сообщением.
- Приёмка: 11-й скан за день → понятный отказ; при выставленном лимите $1 предохранитель срабатывает на тесте.
- Артефакт: `docs/tasks/T3.4.md`.

### Волна 4 — сборка и полевой тест (2 агента + человек)

**T4.1 Устойчивость**
- Вход: чек-лист пайплайна §11.
- Выход: прогон всех 7 пунктов чек-листа с доказательствами (логи/скрины) в артефакте; исправление найденного.
- Приёмка: все пункты отмечены с ссылкой на доказательство.
- Артефакт: `docs/tasks/T4.1.md`.

**T4.2 Сборка и полевой тест**
- Выход: EAS-сборка (TestFlight + APK); demo-сценарий §0 пройден на реальном пляже 20 раз подряд; таблица: скан → тир → время → стоимость → совпадение с ожиданием; 3 переснятых камня — стабильность тира.
- Приёмка: ≥ 18 из 20 сканов дали карточку за ≤ 5 с; стабильность тира ≥ 80 % (для прототипа; 90 % — цель v1); средняя стоимость ≤ $0.03.
- Артефакт: `docs/tasks/T4.2.md` — итоговый отчёт прототипа.

## 5. Правила для агентов

1. Читать `rock-game-spec.md` и `rock-game-ai-pipeline.md` перед задачей. Противоречие между ними и этим планом — фиксировать в артефакте, не решать молча.
2. Не расширять scope. Всё, что «было бы логично добавить», — в раздел «Не сделано» артефакта.
3. Числа score, пороги, таблицы — только из `packages/shared`. Дублирование чисел в клиенте или воркере — дефект.
4. Модель не вызывается из клиента. Ключи только в воркере.
5. Каждый вызов модели логируется: `scan_id, stage, provider, model, prompt_version, tokens_in/out, cost_usd, latency_ms`.
6. Тесты — часть задачи, не отдельная задача. Задача без проходящих тестов не принята.
7. Артефакт `docs/tasks/<ID>.md` пишется по ходу, а не в конце — чтобы упор в лимит контекста не терял результат.
8. Промпты не менять без прогона `pnpm eval` и записи дельты в артефакт.

## 7. Оценка

| Волна | Агентов | Календарно |
|---|---|---|
| 0 | 1 | 1 день |
| 1 | 4 | 2–3 дня |
| 2 | 4 | 3–4 дня |
| 3 | 4 | 2–3 дня |
| 4 | 2 + полевой тест | 2–3 дня |
| **Итого** | | **~2 недели до прототипа в руках** |

Календарь предполагает, что человек в цикле принимает волну за полдня и сам проводит полевой тест. Golden set на 60 фото — узкое место: фото ловушек нужно найти или снять руками, агент это не сделает.

## 8. Что после прототипа (не делать сейчас)

Порядок из ТЗ §14: golden set до 300 → верификация сообществом → обмен → собственный классификатор на подтверждённых сканах → подписка → grading → рынок. Каждый следующий шаг — по метрикам предыдущего, не по плану.
